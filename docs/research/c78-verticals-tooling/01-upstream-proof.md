## Open questions for fork-auditor / devil's advocate

1. **neural-trader native `mcp__ruflo-sublinear__*` path — does the fork register it, and is the speedup real?** Upstream's CG + PageRank kernels self-disclose the native tool's absence and fall through to the embedded JS (`method:"cg-local"`/`Path:local`). The README claims 40-60× (CG) and native-WASM PageRank once `ruflo-sublinear` is registered. Does the fork (a) ship/register `mcp__ruflo-sublinear__solve` + `…__page-rank-entry` (so the native path runs, FORK-AHEAD — verify the 40-60× and the `‖cg−neumann‖∞ < 1e-4` parity hold natively), (b) keep the honest local fallback (PARITY), or (c) advertise the native tool but no-op it (the C1 `hooks_transfer`-class fabrication risk)? Drive `solveCG` against the fork with the tool registered and confirm `method:"cg-sublinear-native"` with real numbers.

2. **neural-trader signing host-dependency (`@noble/ed25519`) — does the fork bundle it?** The plugin ships no package.json; the signing `.mjs` `import '@noble/ed25519'` (host-provided). If the fork's CLI doesn't bundle `@noble/ed25519`, `trader-backtest`/`trader-explain` signing throws `ERR_MODULE_NOT_FOUND` at the host — the skills' "NEVER silently fall back; store UNSIGNED with a loud warning" path should engage. Confirm the fork (a) bundles `@noble/ed25519`, and (b) the UNSIGNED-degraded warning actually fires (not a silent throw) when the dep is missing. This is the paper→live promotion gate — a silent signing failure would be a real security regression.

3. **iot-cognitum coordinator persistence — does the fork persist device state?** Upstream uses `InMemoryDeviceRepository`/`InMemoryFleetRepository`/`InMemoryTrustHistoryRepository` — device state dies with each one-shot CLI process; the lifecycle is coherent only in a long-lived MCP server. Drive register-then-status as SEPARATE fork CLI processes; if status finds the device, the fork persists.
