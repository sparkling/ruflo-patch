# MCP Server Wiring Soundness Audit (Slice 09)

ADR-0201 read-only static audit. Scope: MCP server startup, transport, tool
registration, dual `ruflo` / `claude-flow` namespace per ADR-0117, plugin MCP
registration, and the wire-up of `@claude-flow/mcp` package facilities
(rate-limiter, connection-pool, OAuth, sampling, prompt-registry,
schema-validator). Cross-reference: `.mcp.json` shape vs init template emission.

## Summary

The MCP server is **NOT** sound and **NOT** complete as architected. There are
**two parallel server implementations** that diverge in protocol version,
tool surface, and security wiring:

- **`@claude-flow/mcp/src/server.ts` (the standalone package)** — full
  MCP 2025-11-25 implementation: protocol version object, OAuth 2.1 + PKCE,
  rate-limiter, connection-pool, sampling manager, prompt registry, resource
  registry, task manager, schema-validator wired into the tool-registry
  execute path, three transports (stdio/http/websocket) with auth on HTTP +
  WebSocket. 1,134 lines.
- **`@claude-flow/cli/src/mcp-server.ts` (the actual `ruflo mcp start`
  entrypoint)** — a hand-rolled JSON-RPC stdio loop (lines 426-722) that
  bypasses the `@claude-flow/mcp` package entirely for the
  user-facing stdio path. Advertises a different `protocolVersion`
  (`'2024-11-05'` string), no rate-limiter, no connection-pool, no OAuth,
  no sampling, no prompt registry, no schema validation per call, and a
  separate `TOOL_REGISTRY` (`mcp-client.ts`) holding 197 tools. 1,016 lines.

The HTTP transport path *does* use the `@claude-flow/mcp` package, but
**none of the 197 CLI tools** are registered with that server — only the
four built-in `system/*` and `tools/list-detailed` tools from
`registerBuiltInTools()`. So `ruflo mcp start --transport http` would
serve a different and much smaller tool surface than stdio.

Plugins do NOT register MCP servers via plugin manifests. The 33
`plugins/ruflo-*/.claude-plugin/plugin.json` files carry only
`name/description/version/keywords` — no `mcpServers` block. ADR-0117
"marketplace MCP server registration" is documented in
`ruflo-core/README.md` (as prose: "registers the `ruflo` MCP server") but
no executable mechanism in the plugin manifests does so. The MCP server is
registered via the project-level `.mcp.json` generated by `init/mcp-generator.ts`.

The dual `ruflo` / `claude-flow` namespace per ADR-0117 IS in place for the
generated `.mcp.json` key (always `'ruflo'`, per `mcp-generator.ts:79`),
**but** the init template never emits `'claude-flow'` as a parallel server
key — meaning `mcp__claude-flow__*` tool references in agent docs only
resolve via legacy installs. Tool names themselves use neither namespace
prefix in the registry (they are bare `agent_spawn`, `memory_store`, etc.);
Claude Code prepends the server key (`ruflo`) at MCP tool surfacing time.

Real issues:

1. **F-09-001 (CRITICAL)** — `tools/call` in `cli/src/mcp-server.ts:655-685`
   never invokes `validateToolInput()`. Inputs go directly to the tool
   handler without any JSON-Schema check.
2. **F-09-002 (CRITICAL)** — HTTP transport in `cli/src/mcp-server.ts:727-756`
   spawns the `@claude-flow/mcp` `MCPServer` but registers zero of the 197
   CLI tools. The package's `registerBuiltInTools()` only adds 4 system
   tools. HTTP mode exposes a different tool surface than stdio.
3. **F-09-003 (HIGH)** — Protocol version split: stdio advertises
   `'2024-11-05'` (string), package server advertises
   `{ major: 2025, minor: 11, patch: 25 }` (object). Same MCP server brand,
   two protocol claims.
4. **F-09-004 (HIGH)** — Rate-limiter, connection-pool, OAuth, sampling,
   prompt-registry, resource-registry, task-manager all exist in the
   `@claude-flow/mcp` package but are NEVER instantiated on the stdio path
   (the user-facing path). They're dead code for the production install.
5. **F-09-005 (MEDIUM)** — Plugin marketplace MCP registration is prose-only.
   `plugins/ruflo-core/.claude-plugin/plugin.json` describes "registers the
   ruflo MCP server" but the manifest has no executable hook to do so;
   actual registration depends on `init/mcp-generator.ts` writing `.mcp.json`.
6. **F-09-006 (MEDIUM)** — `tool-registry.ts` (the package version) DOES wire
   `validateSchema` on every `execute()` (line 286-299), but this code path
   is unreached by stdio (which uses `mcp-client.ts`'s `callMCPTool` instead).
7. **F-09-007 (MEDIUM)** — The CLI's `validateToolInput` (`mcp-client.ts:270-299`)
   is a weaker variant of the package's `validateSchema` — only checks
   `required` fields, ignores `type`, `pattern`, `minLength`, `maxLength`,
   `minimum`, `maximum`, `enum`, `additionalProperties`. Even if it were
   wired, it would not provide JSON-Schema enforcement.
8. **F-09-008 (LOW)** — `WebSocket` transport in `mcp/src/transport/http.ts`
   binds at `/ws` on the same HTTP port (line 78-81); authentication checks
   the `Authorization` Bearer header on HTTP but accepts the token via URL
   `?token=` on WebSocket. Two auth surfaces, same server.
9. **F-09-009 (LOW)** — `cli/src/mcp-server.ts:432-436` says "Log to stderr
   to not corrupt stdout" but then line 512-521 writes a `console.error`
   structured-JSON env block AND line 524-537 writes the `server.initialized`
   notification to `console.log` (stdout) — the stdout write is fine per
   MCP, but the env-block is JSON-shaped on stderr without a JSON-RPC envelope
   and would be mistaken for a JSON-RPC message by any reader that doesn't
   strictly separate the streams.
10. **F-09-010 (INFO)** — `connection-pool.ts` is for in-process pooled
    connections, not network connection pooling; the `IConnectionPool` is
    instantiated only when `config.connectionPool` is set (line 145-151 of
    `server.ts`), which the CLI never does. The pool exists as a facility
    no caller currently configures.

## Findings

### F-09-001 [CRITICAL] tools/call bypasses schema validation in production stdio path

- File: `/Users/henrik/source/forks/ruflo/v3/@claude-flow/cli/src/mcp-server.ts:655-685`
- Sound: NO — JSON-RPC `tools/call` invokes `callMCPTool(toolName, toolParams, ...)` with no schema check. Tool handlers must defend themselves; many do not.
- Complete: PARTIAL — `mcp-client.ts:270-299` exports `validateToolInput`, never called.
- Evidence:

```
case 'tools/call':
  const toolName = params.name as string;
  const toolParams = (params.arguments || {}) as Record<string, unknown>;

  if (!hasTool(toolName)) {
    return { jsonrpc: '2.0', id: message.id,
      error: { code: -32601, message: `Tool not found: ${toolName}` } };
  }

  try {
    const result = await callMCPTool(toolName, toolParams, { sessionId });
    // ... no validateToolInput, no validateSchema, no shape check
```

  `callMCPTool` (mcp-client.ts:156-183) does a Map lookup, runs the handler,
  wraps thrown errors. Zero schema enforcement between the wire and the
  handler. Compare against `mcp/src/tool-registry.ts:286-299` which DOES
  validate against `tool.inputSchema` on every `execute()` — but that
  code path is reached only when HTTP transport is selected, and even
  then no real tools are registered (see F-09-002).

- Suggestion: Either call `validateToolInput` (and upgrade it per F-09-007)
  before `callMCPTool`, or route stdio through the package's
  `MCPServer.handleToolsCall()` path that already wires `validateSchema`.

### F-09-002 [CRITICAL] HTTP transport spawns MCPServer but registers zero tools

- File: `/Users/henrik/source/forks/ruflo/v3/@claude-flow/cli/src/mcp-server.ts:727-756`
- Sound: NO — `startHttpServer()` calls `createMCPServer(...)` then `mcpServer.start()` and stops. No `registerTool` calls anywhere.
- Complete: NO — `mcp/src/server.ts:1036-1094` only registers 4 built-in tools (`system/info`, `system/health`, `system/metrics`, `tools/list-detailed`); the 197 CLI tools live in `mcp-client.ts`'s separate `TOOL_REGISTRY`, never copied across.
- Evidence:

```
const { createMCPServer } = await import('@claude-flow/mcp');
const mcpServer = createMCPServer({...}, logger);
await mcpServer.start();
(this as any)._mcpServer = mcpServer;   // store reference, that's it
```

  `mcpServer.start()` calls `registerBuiltInTools()` (server.ts:233) which
  registers only 4 tools. No bridge wires `mcp-client.ts`'s `TOOL_REGISTRY`
  into `mcpServer.registerTools(...)`.

  Practical effect: `ruflo mcp start --transport http -p 8080` would respond
  to `tools/list` with 4 tools, not 197. Tests probing tool surface across
  transports would see different answers depending on transport.

- Suggestion: After `mcpServer.start()`, iterate `mcp-client.ts`'s registry
  and call `mcpServer.registerTools(...)`. Or refactor to a single registry
  source-of-truth.

### F-09-003 [HIGH] Protocol version disagrees between stdio and HTTP transports

- File: `/Users/henrik/source/forks/ruflo/v3/@claude-flow/cli/src/mcp-server.ts:632` vs `/Users/henrik/source/forks/ruflo/v3/@claude-flow/mcp/src/server.ts:91-95,492`
- Sound: NO — same `MCPServer V3` brand returns two different protocol versions depending on which transport was selected at startup.
- Complete: PARTIAL — both stubs are real values; neither is missing.
- Evidence:

```
# cli/src/mcp-server.ts:626-639 (stdio path)
case 'initialize':
  return { jsonrpc: '2.0', id: message.id, result: {
    protocolVersion: '2024-11-05',                // STRING, MCP 2024-11-05
    serverInfo: { name: 'ruflo', version: '3.0.0' }, ... } };

# mcp/src/server.ts:91-95 (HTTP/WebSocket path)
private readonly protocolVersion: MCPProtocolVersion = {
  major: 2025, minor: 11, patch: 25,                // OBJECT, MCP 2025-11-25
};
```

  Stdio sends a string; package sends an object. The MCP spec uses date-
  stamped strings like `"2025-11-25"` — both are non-canonical (one is
  the wrong date, the other is the wrong shape).

- Suggestion: Pick one. The package's `{major, minor, patch}` object is not
  the wire shape MCP spec uses; the stdio's `'2024-11-05'` string is wire-
  conformant but a year stale. Replace both with `'2025-11-25'` string,
  or replace both with the structured object if the spec is being
  intentionally extended.

### F-09-004 [HIGH] Package facilities (rate-limiter, connection-pool, OAuth, sampling, prompt-registry, resource-registry, task-manager) never wired for stdio

- File: `/Users/henrik/source/forks/ruflo/v3/@claude-flow/mcp/src/{rate-limiter,connection-pool,oauth,sampling,prompt-registry,resource-registry,task-manager}.ts` (all instantiated in `mcp/src/server.ts:122-152`); never reached from `cli/src/mcp-server.ts`.
- Sound: NO — eight subsystems documented as part of the MCP V3 architecture; production stdio path skips all of them.
- Complete: NO — facilities exist in source; never instantiated on the user-facing path.
- Evidence:

```
# mcp-server.ts (CLI stdio path) imports:
import { trackRequest } from './mcp-tools/request-tracker.js';
# That's the only "supporting" subsystem. No rate-limiter, no connection-pool,
# no OAuth, no sampling, no prompt registry, no resource registry, no task manager.

# mcp/src/server.ts:122-152 (the unused server) wires:
this.toolRegistry = createToolRegistry(logger);
this.sessionManager = createSessionManager(logger, ...);
this.resourceRegistry = createResourceRegistry(logger, ...);
this.promptRegistry = createPromptRegistry(logger);
this.taskManager = createTaskManager(logger, ...);
this.transportManager = createTransportManager(logger);
this.rateLimiter = createRateLimiter(logger, ...);
this.samplingManager = createSamplingManager(logger);
```

  Every one of these subsystems has nontrivial code (oauth.ts: 448 lines,
  sampling.ts: 363, prompt-registry.ts: 297, resource-registry.ts: 14KB,
  rate-limiter.ts: 267) that is never reached when a user runs
  `ruflo mcp start` (the default stdio path).

  HTTP path partially activates them (via `mcp/src/server.ts`), but per
  F-09-002 the HTTP path is broken for real tool surface.

- Suggestion: Either retire the parallel `cli/src/mcp-server.ts` stdio
  implementation and route stdio through the package's `MCPServer`
  (preserving its rate-limiter / validation wiring), or explicitly mark
  these subsystems as HTTP-only and document that fact.

### F-09-005 [MEDIUM] Plugin marketplace MCP server registration is prose-only

- File: `/Users/henrik/source/forks/ruflo/plugins/ruflo-core/.claude-plugin/plugin.json` (plus 32 sibling plugins)
- Sound: PARTIAL — the project-level `.mcp.json` (generated by ruflo init) does register the server. But plugin manifests themselves do not — the README claim "registers the ruflo MCP server" is descriptive of the system, not enforced by the plugin manifest.
- Complete: NO — no plugin manifest contains an `mcpServers` block (verified via `grep -r mcpServers plugins/`); the plugin install path does not add to or modify `.mcp.json`.
- Evidence:

```
# plugins/ruflo-core/.claude-plugin/plugin.json — entire content:
{
  "name": "ruflo-core",
  "description": "Foundation plugin — registers the ruflo MCP server (300+ tools ...) ...",
  "version": "0.2.17",
  "author": { ... },
  "homepage": "...",
  "license": "MIT",
  "keywords": [...]
}

# grep -r mcpServers plugins/  →  (empty)
# grep -r registerMcpServer plugins/  →  (empty)
```

  ADR-0117 ("marketplace MCP server registration") documents that plugins
  register MCP servers under the `ruflo` key (so `mcp__ruflo__*` references
  resolve), but the plugin manifest has no field to do this. The README in
  ruflo-core lists 300+ tools but no code in the plugin causes those tools
  to be registered. They are registered by the `@sparkleideas/cli` package
  loaded via `npx`, regardless of which plugins are installed.

  Practical effect: `plugin install ruflo-core@ruflo` only installs agents
  / commands / skills / hooks bundles. The MCP server itself is registered
  by `.mcp.json` (output of `ruflo init`). The plugin contributes nothing
  to MCP tool surface.

- Suggestion: Either remove "registers the ruflo MCP server" from the
  plugin description (it's misleading — the plugin doesn't), or add a
  real plugin-manifest-based MCP server registration path (would need
  Claude Code plugin loader support).

### F-09-006 [MEDIUM] tool-registry.ts validateSchema unreachable from stdio

- File: `/Users/henrik/source/forks/ruflo/v3/@claude-flow/mcp/src/tool-registry.ts:286-299`
- Sound: PARTIAL — the validation IS correct and IS wired in the package's `execute()` path; just not reachable from the user-facing stdio entrypoint.
- Complete: PARTIAL — the package's tool-registry is fully complete; it just isn't used in the stdio request loop.
- Evidence:

```
# mcp/src/tool-registry.ts:286-299
if (metadata.tool.inputSchema) {
  const validation = validateSchema(input, metadata.tool.inputSchema);
  if (!validation.valid) {
    const errorMsg = formatValidationErrors(validation.errors);
    return { content: [{ type: 'text', text: `Invalid input: ${errorMsg}` }],
             isError: true };
  }
}
```

  This wires the full schema-validator on every `tool-registry.execute()`.
  Compare against `cli/src/mcp-client.ts:callMCPTool` which calls
  `tool.handler(input, context)` directly with no validation.

- Suggestion: Route stdio through the package's `MCPServer`, or copy this
  validation into `mcp-client.ts:callMCPTool`.

### F-09-007 [MEDIUM] CLI's validateToolInput is a weaker variant of validateSchema

- File: `/Users/henrik/source/forks/ruflo/v3/@claude-flow/cli/src/mcp-client.ts:270-299`
- Sound: PARTIAL — the function exists, but even when called it only checks `required`. Compare to package's `schema-validator.ts:25-180` which covers `type`, `pattern`, `minLength/maxLength`, `minimum/maximum`, `enum`, `additionalProperties`, nested objects, array items.
- Complete: NO — even if wired (per F-09-001), it would not provide JSON-Schema enforcement.
- Evidence:

```
# cli/src/mcp-client.ts:283-293
const schema = tool.inputSchema;
const errors: string[] = [];

if (schema.required && Array.isArray(schema.required)) {
  for (const requiredField of schema.required) {
    if (!(requiredField in input)) {
      errors.push(`Missing required field: ${requiredField}`);
    }
  }
}
```

  No type-check, no pattern, no bounds, no enum, no `additionalProperties`,
  no nested validation. A schema declaring
  `{type: 'integer', minimum: 0, maximum: 100}` is enforced as "field
  exists".

- Suggestion: Replace with import from `@claude-flow/mcp/schema-validator`,
  or delete and route through package's MCPServer.

### F-09-008 [LOW] HTTP and WebSocket auth surfaces differ

- File: `/Users/henrik/source/forks/ruflo/v3/@claude-flow/mcp/src/transport/http.ts:286-322` (WS) vs `:495-524` (HTTP)
- Sound: PARTIAL — both validate, but via different inputs.
- Complete: YES — both reject unauthenticated requests; uses timing-safe compare.
- Evidence:

```
# WebSocket (line 290-297):
const token = url.searchParams.get('token') || req.headers['authorization']?.replace(/^Bearer\s+/i, '');
# HTTP (line 502-507):
const tokenMatch = auth.match(/^Bearer\s+(.+)$/i);
```

  WebSocket accepts the token as `?token=...` query parameter; HTTP only
  accepts `Authorization: Bearer ...`. URL query strings appear in access
  logs and HTTP referer headers; recommendation is to accept only via
  header for WS too.

- Suggestion: Standardise on `Authorization: Bearer` for both transports.

### F-09-009 [LOW] CLI stdio start writes stderr JSON-shaped log without JSON-RPC envelope

- File: `/Users/henrik/source/forks/ruflo/v3/@claude-flow/cli/src/mcp-server.ts:512-521`
- Sound: PARTIAL — stderr is allowed for log output per MCP spec, but a JSON-shaped object on stderr is easily mistaken for a JSON-RPC frame.
- Complete: YES — code does what it claims; it's a stylistic / interop concern.
- Evidence:

```
console.error(JSON.stringify({
  arch: process.arch, mode: 'mcp-stdio', nodeVersion: process.version,
  pid: process.pid, platform: process.platform, protocol: 'stdio',
  sessionId, version: VERSION,
}));
```

  A reader that doesn't strictly separate stdout / stderr (and some test
  harnesses do not) would parse this as a JSON-RPC frame and fail because
  it lacks `jsonrpc`, `id`, `method`. Other log lines (line 435-436) are
  human-readable strings — only this one is JSON-shaped.

- Suggestion: Wrap structured logs in `{ jsonrpc: '2.0', method:
  'notifications/message', params: {...} }` or emit as human-readable.

### F-09-010 [INFO] connection-pool is in-process only and never configured

- File: `/Users/henrik/source/forks/ruflo/v3/@claude-flow/mcp/src/connection-pool.ts` (345 lines), instantiated only if `config.connectionPool` is set (`mcp/src/server.ts:145-151`).
- Sound: YES — code is a faithful in-process pool of `PooledConnection` objects.
- Complete: NO — no caller in either CLI's mcp-server.ts or anywhere in v3 sets `config.connectionPool` when creating `MCPServer`. The pool is dead code.
- Evidence: `grep -r "connectionPool" /Users/henrik/source/forks/ruflo/v3/@claude-flow/cli/src/` returns 0 hits in the active CLI code path.
- Suggestion: Either wire it for HTTP transport (where multiple concurrent

## Cross-cutting note: dual-namespace claim from ADR-0117

The claim "tools exposed under `ruflo` per ADR-0117" is true for the
generated `.mcp.json` server key (`mcpServers.ruflo` per `mcp-generator.ts:79`).
However:

- Tool NAMES (e.g. `agent_spawn`, `memory_store`, `agentdb_health`) carry
  neither `ruflo_` nor `claude-flow_` prefix in the registry. Claude Code
  prepends the server key at surface time, producing `mcp__ruflo__agent_spawn`.
- The init template never emits a second `mcpServers.claude-flow` key.
  Any tool reference in older agent docs that uses `mcp__claude-flow__*`
  will only resolve if a legacy `.mcp.json` registered a `claude-flow` key.
  New projects from `ruflo init` get a single `ruflo` key.
- The `ruflo` wrapper bin (`forks/ruflo/ruflo/bin/ruflo.js:33-37`) detects
  MCP mode by `isExplicitMCP = cliArgs[0] === 'mcp' && (cliArgs.length === 1 || cliArgs[1] === 'start')`
  and falls through to `cli.js`, so `ruflo mcp start` and
  `claude-flow mcp start` end up in the same code path; the namespace
  distinction is purely the wrapper's branding text. No tool surfaces or
  protocol behaviour differ.

If the intent of ADR-0117 was to provide a dual-namespace tool surface
(so `mcp__ruflo__*` AND `mcp__claude-flow__*` both resolve), the init
template would need to emit two `mcpServers` keys, both pointing at the
same `npx -y @sparkleideas/ruflo@latest mcp start` command. Currently
it emits only one.

## Init template emission

`init/mcp-generator.ts:79-89` emits exactly the canonical shape captured
in `/Users/henrik/source/ruflo-patch/.mcp.json`. Verified match:

```
{
  "mcpServers": {
    "ruflo": {
      "command": "npx",
      "args": ["-y", "@sparkleideas/ruflo@latest", "mcp", "start"],
      "env": { npm_config_update_notifier, CLAUDE_FLOW_MODE,
               CLAUDE_FLOW_HOOKS_ENABLED, CLAUDE_FLOW_TOPOLOGY,
               CLAUDE_FLOW_MAX_AGENTS, CLAUDE_FLOW_MEMORY_BACKEND },
      "autoStart": true
    }
  }
}
```

Confirmed:

- `command` is `npx` per `feedback-always-npx-for-ruflo`.
- Args use `@sparkleideas/ruflo@latest` per ADR-0143 (user-facing brand).
- `@latest` resolution is dynamic per `feedback-always-npx-for-ruflo`
  (freshness wins; cold-start cost accepted).
- Five `CLAUDE_FLOW_*` env vars are flowed through from
  `options.runtime`. The MCP server itself only reads `CLAUDE_FLOW_MODE`
  (`v3` branch) and `CLAUDE_FLOW_HOOKS_ENABLED` reactively; topology /
  maxAgents / memoryBackend are consumed downstream by swarm-init and
  memory-router.

Init template emission is sound and complete.
